# Key Patterns & Important Notes

## Key Patterns

- **Streaming**: SSE with event types `text_delta`, `thinking_delta`, `tool_status`, `artifact`, `ask_user`, `done`, `error`, `iteration`, `warning`, `compaction`, `title_update`, `message_complete`, `follow_up_start`
- **Types**: Shared interfaces in `server/src/types.ts` and `client/src/types.ts` (kept in sync manually)
- **Storage**: SQLite for chats/projects/settings/pending/automations/push subscriptions/SSH connections (`chat-storage.ts` → `~/.porrima/app.db`), SQLite + sqlite-vec + FTS5 for memories and blocks (`memory-storage.ts` → `~/.porrima/memory/memories.db`), and a separate observability database for model + reranker samples (`~/.porrima/porrima.db`). Notebooks are **not** file-backed in normal operation: user entries are the `user_notebook_entries` table (+ FTS5) in `memories.db`, and agent entries are `memory_blocks` rows with `blockType IN ('notebook','synthesis')`. `~/.porrima/notebooks/` is retained only as the one-time JSON migration source/backup. All use `~/.porrima/` as the base directory. See [data-storage.md](data-storage.md).
- **Chat message rows**: `chat_message_rows` is the full-fidelity message source keyed by `(chat_id, sequence)`; `chats.messages` remains a compatibility snapshot. Initial chat fetches use a recent message window (`messageLimit`, default client value 200), and older windows load by absolute `before` sequence.
- **Tool-loop persistence**: Tool-use iterations are persisted as canonical split assistant rows grouped by `_toolLoopId`, with `_toolLoopFragment` on rows that end in tool calls. Do not collapse those rows into one assistant message; replay must preserve the live pi-ai transcript shape for llama.cpp longest-common-prefix KV cache reuse. Tool results are additionally re-sorted into assistant **call order** by `tool-result-ordering.ts` before persistence, because tool execution can complete in a different order than the assistant emitted the calls.
- **Tool result wire shape**: `normalizeToolResultContent()` in `agent-tools.ts` runs at the execute boundary and strips every tool result to the strict `{ type: "text" | "image" }` item shape (converting bare strings to a single text item). Tool results enter both the live wire context and the persisted row, so any extra field an executor attaches would ride the wire but vanish on replay, causing a KV-cache digest divergence and a full re-prefill.
- **Time markers**: `wrapToolsWithTimeMarker()` appends an elapsed-time line (`[time: HH:MM — Nm since last marker]`) to the *tail* of a tool result before it reaches either the live wire or the persisted row, gated by `settings.timeMarkerIntervalMinutes` (0/unset disables). The first marker measures from turn start, later markers from the previous marker, so the model reconstructs the clock by summing deltas. The check-and-set is synchronous, so a parallel batch can never emit two markers.
- **Shared agent loop**: `agent-loop-runner.ts` is the low-level `agentLoop` / `agentLoopContinue` driver used by the HTTP chat route and headless system/automation turns. Prompt construction, history mutation, compaction, SSE emission, and persistence stay caller-owned so KV-cache-sensitive replay shape remains explicit.
- **LLM providers**: Single registered pi-ai provider — `openai-compat` for llama.cpp / OpenAI-format servers. `discoverAllModels()` queries the llama.cpp server; `createPiModelFromProvider()` creates openai-compat models. llama.cpp router mode tracks `lastLoadedModel` to minimize model swap overhead.
- **llama.cpp prompt cache observability**: `openai-compat-provider.ts` explicitly sends `cache_prompt: true` for `/v1/chat/completions` unless `LLAMACPP_CACHE_PROMPT=0` is set. Final llama.cpp timing chunks are recorded in `model-stats.ts` with request size, reported prompt tokens, prompt eval tokens, and inferred cached-token counts; the client surfaces them in the Model Stats & Cache modal.
- **Context window**: Fetched per-model from llama.cpp `/v1/models` metadata and `/props`. Per-chat override via `chat.contextWindow`; effective value is `chat.contextWindow ?? model.contextWindow`.
- **Embeddings**: llama.cpp `qwen3-embedding:0.6b` via `POST http://localhost:32103/v1/embeddings`. Vectors are L2-normalized, so cosine similarity = dot product.
- **Memory retrieval**: Hybrid search (vector + FTS5) → RRF fusion → cross-encoder reranking (Qwen3-Reranker-0.6B on port 32102) with chat-type-specific instructions → MMR diversity selection. Reranker scores replace RRF scores (0-1 calibrated). Retrieved memories use KV-cache-aware injection: frozen set in system prompt (first turn/post-compaction), new memories appended as delta messages before the next user message, and passive mid-turn recalls appended before later provider calls during long tool loops. `MemoryContextState` tracks `frozenIds` and `deltaIds`; passive recall also excludes already in-context/injected IDs. Hidden persisted system rows replay as synthetic user-role context messages because mid-transcript system roles are not provider-stable. `[kv-cache]` logs correlate with llama.cpp prompt eval stats.
- **Memory scoring**: `rrf_score * recency_decay * (importance / 10)` with RRF combining vector search and FTS5 full-text search rankings; 30-day half-life on recency. Context estimation returns max of two paths — usage-anchor (last in-context assistant's `usage.totalTokens` + deltas) and pure char-based — so a stale anchor can't under-count. See the compaction-ratios bullet above for the three pre-send triggers (0.85 / 0.95 / 1.15) and the 0.80 end-of-turn threshold.
- **Memory blocks**: Structured knowledge documents (`memory_blocks` table + FTS5) loaded by scope (global/project) into system prompt. 4000 char limit per block with supersession versioning. Extraction prompt includes block content to prevent redundant fact extraction. `search_memory` returns block excerpts alongside atomic results. Stable prefix caching in `stablePrefixCache` keeps blocks and frozen memories in a cached prefix for KV cache optimization; new memories injected as deltas to preserve longest-common-prefix caching.
- **Memory dedup**: cosine > 0.85 between a new fact and existing memory triggers UPDATE instead of ADD. Uses sqlite-vec KNN MATCH for nearest-neighbor lookup.
- **Supersession tracking**: memories can be linked via `superseded_by` / `supersedes` columns when contradicted or updated. Confidence threshold (default 0.75) determines automatic linking; manual override via API.
- **Delayed extraction**: time-based trigger (configurable, default 30 min) extracts memories from inactive chats. Uses `updateChatExtractionState()` to avoid modifying `lastModified` (preserves chat ordering).
- **Project scoping**: memories have optional `projectId`; synthesis groups chats and memories by project, loading each project's AGENTS.md for context.
- **Automations**: `automation-scheduler.ts` checks enabled tasks every 5 minutes, ordered by `orderIndex`, and starts one due task per tick. Built-ins cover synthesis and wake; custom tasks run in system chats with editable interval/daily schedules, prompt steps, activation policies, notifications, run history, failure backoff, and auto-disable after repeated custom failures.
- **Idle VRAM reclamation**: llama.cpp slots run `--sleep-idle-seconds 172800`, which permits long-idle unloading without clearing the prompt cache between ordinary follow-up messages. Title generation uses CPU-only instances to avoid VRAM competition.
- **Indexed compaction**: Compacted messages archived in `context_archives` table (not discarded). Index descriptions are written in `sync` mode (end-of-turn, mid-turn, `/compact`) or `deferred` mode (pre-send: mechanical description first, background LLM enrichment after) so the user turn isn't blocked on the CPU model. `read_archived_context` tool dereferences archive IDs. FTS5 enables cross-chat search of archived content. Compaction summaries are filtered from memory extraction to prevent metadata pollution. The primitive is: collect removed → await `onBeforeArchive` (the flush) → archive & index → mark `_outOfContext` / clear stale `usage` → splice summary; the soft reset and prompt rebuild are **caller-owned**. Compaction soft-resets (`softResetMemoryContext`) — it keeps the frozen set byte-exact so the next build is a delta; a hard reset is used only for chat deletion and cache-warm preparation (automation and system-chat runs retain the frozen set). Clearing every kept assistant `usage` leaves the estimator with no anchor, so `selectedPath` falls back to `char_estimate` and only the 0.95 hard cap is live until the next provider call reports usage. The memory flush is **HTTP-only** — headless paths pass `undefined` for the hook. See [compaction.md](compaction.md).
- **Mid-turn compaction**: Detects context pressure during tool loops, breaks the agent loop, persists any uncommitted assistant work, archives + compacts, awaits preCompactionFlush, rebuilds system prompt, fetches chat memories, assembles handoff message (progress summary + memories), resumes via `agentLoopContinue`. Up to 5 cycles on the HTTP path, **3** on the headless path.
- **Compaction ratios**: pre-send has three triggers — normal 0.85 against the usage-anchored `refinedTokens`, an anchor-bounded hard cap at 0.95, and a pure char estimate at **1.15**. End-of-turn fires at **0.80**, earlier than pre-send, because it runs while the user reads rather than waits.
- **Tool result limits**: Dynamic truncation at 15% of context window (min 8k chars). Formula: `Math.max(8000, contextWindow * 4 * 0.15)`.
- **Deferred extraction**: Memory extraction during active tool loops is queued (not fire-and-forget) and executed after the agent loop completes to prevent concurrent LLM calls.
- **Background work holds the turn lease**: GPU-bound background jobs (cache warms, wake cycles) acquire the same per-chat turn lease real turns use, tagged `kind: "cache-warm"` with `priority: "background"` and a 60s heartbeat. Without it, a turn arriving mid-warm dispatches immediately, llama.cpp queues it invisibly behind the warm, and the turn's prefill monitor latches onto the warm's slot instead. A foreground turn additionally **preempts** a running background warm, while a user-requested warm is never preempted. `isCacheWarmOrLlamaRuntimeBusy()` implements the reverse check: a *timed-out* probe counts as busy, because a slow HTTP warm can still be burning GPU.
- **Artifact review**: `artifact-preview.ts` renders the just-written version of an artifact/visual in headless Chrome (launched with `--enable-unsafe-webgpu --ignore-gpu-blocklist` so WebGPU artifacts render) and attaches a PNG to the tool result. The preview resolves the *specific version directory*, so the screenshot always matches the version just written. `agent-tools.ts` caps automatic screenshot-driven `update_artifact` calls at 2 per artifact/visual per turn. There is no multi-iteration image-generation-with-agent-review subsystem.
- **No image-generation tool**: `agent-tools.ts` registers no image generation or vision-analysis tool. The agent can only *ingest* images — `read_pdf(extractImages=true)` returns inline figures, `browser_screenshot` returns page images, and artifact previews return render screenshots. Image generation and analysis live in a separate app.
- **Tool result images**: any image emitted as a tool result is written to `~/.porrima/tool-result-images/{id}/image.{ext}` and served from `/api/tool-result-images/{id}/image.{ext}`; the base64 `data` is stripped from the persisted chat row and re-hydrated on replay (`tool-result-image-storage.ts`). Both the HTTP chat path and the headless automation path externalize.
- **Inline local image refs**: markdown images pointing at local paths (`/tmp/...`, `~/...`, `file://`) are *not* externalized or rewritten in storage — the persisted row and wire context stay untouched (KV-cache parity). `MarkdownImage` rewrites the src to `/api/local-images?path=...` at render time and the server serves the file from disk when it exists (allowed roots + magic-byte image check + 64 MB cap; `local-image-serving.ts`). When the scratch file is gone the client shows an inline "image unavailable" note.
- **Backward compat**: `getChat()` maps a missing/unknown `type` to "agent". A one-time migration (`remove-quick-chats`) deletes legacy quick chats and their rows, since the quick chat type was removed. Memory DB auto-migrates `project_id` column. Chat/project/settings JSON files auto-migrate to SQLite on startup, and legacy chat JSON snapshots backfill `chat_message_rows`. Legacy collapsed tool rows still replay through the old expansion path.

## Important Notes

- The `memory.ts` routes must define `/status`, `/synthesis/*`, and `/search` **before** the `/:id` param routes to avoid Express matching those paths as IDs.
- `streamChat` from `agent.ts` is for one-shot LLM calls. Tool-loop work uses `runAgentLoop()` through the chat route or `runHeadlessChatTurn()`.
- The scheduler (`scheduler.ts`) starts the configurable automation scheduler and delayed extraction. Automations check every 5 minutes; delayed extraction checks every 5 minutes.
- Automation defaults are ensured once during server startup in `index.ts`, not on every scheduler tick or route request.
- When editing types, update both `server/src/types.ts` and `client/src/types.ts`.
- The server may run compiled `dist/index.js` (via `npm start` / systemd) rather than tsx dev mode — source changes require `npm run build` + restart to take effect.
- Blob URLs for artifacts are critical for Chrome animation performance — do not use cross-origin iframe src.
- llama.cpp provider uses router mode with `--models-dir`. Model directory structure: subdirectory per model with GGUF + optional mmproj for vision. `sync-llama-models.sh` auto-syncs HuggingFace downloads. HF-cached models (IDs with `/`) filtered from discovery. Context window set on first load only — no mid-conversation reloads.
- **llama.cpp binary management**: All five services reference `~/bin/llama-current/llama-server` by default. Per-slot binary overrides via `settings.llamaServerBins[slotId]`. Custom binaries get auto-injected `LD_LIBRARY_PATH`. Symlink updates via Settings → Binary Path handle swap + restart + rollback. Service configs (port, ctx size, extra args, mode) managed via `/api/llama-servers/:id/config` with systemd drop-in override writing.
- Reranker service (`reranker.service`) runs Qwen3-Reranker-0.6B on port 32102, CPU-only, always available. Graceful fallback if unavailable.
- The `extractionModelId` setting allows using a separate model for memory extraction; `extractionFallbackEnabled` controls whether to fall back to the default model if the extraction model is unavailable.
